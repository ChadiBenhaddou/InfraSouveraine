Présentation

InfraSouveraine est une plateforme SaaS multi-tenant qui permet aux professionnels et aux entreprises de déployer des serveurs LLM (Large Language Model) privés et isolés sur des GPU dédiés via l'API cloud RunPod.

La plateforme guide l'utilisateur depuis la description de son cas d'usage jusqu'à l'obtention d'un serveur Open WebUI + Ollama opérationnel, avec un abonnement mensuel à prix fixe.

🎯 Objectifs

  • Isolation totale des données (pod dédié)
  • Déploiement automatisé en < 5 minutes
  • Prix mensuel fixe et prévisible
  • Souveraineté des données (hébergement Europe)

👥 Utilisateurs cibles

  • Cabinet d'avocats (documents confidentiels)
  • Développeurs (assistant de code privé)
  • PME / ETI (données sensibles)
  • Professionnels de santé (RGPD)

Parcours d'onboarding

L'utilisateur traverse un wizard en 5 étapes, géré par le composant Livewire OnboardingWizard.

Étape 1 — Cas d'usage

L'utilisateur décrit son besoin (ex: "assistant juridique pour analyser des contrats").

  • Validation : texte entre 10 et 1000 caractères
  • Un Tenant est créé ou mis à jour
  • Le service AiRecommender est appelé

Étape 2 — Recommandation

OpenAI (GPT-4o-mini) analyse le cas d'usage et retourne un modèle + GPU recommandé. En cas d'échec de l'API, un fallback par mots-clés est utilisé.

Mot-cléModèle par défaut
code, program, developDeepSeek Coder 33B
legal, privacy, documentLlama 3 8B Instruct
creative, write, storyDolphin Mixtral 8x7B
AutreLlama 3 8B Instruct

Étape 3 — Sélection du GPU

L'utilisateur choisit parmi les GPU compatibles avec son modèle (VRAM suffisante).

Étape 4 — Revue et paiement

Récapitulatif du prix mensuel, puis redirection vers PayPal pour souscrire.

Étape 5 — Confirmation

Une fois le paiement approuvé, le job ProvisionRunPodPod est dispatché pour créer le pod GPU.

Service de recommandation IA

app/Services/AiRecommender.php

Interroge GPT-4o-mini avec un prompt système listant les modèles disponibles. Le modèle répond en JSON structuré : 

{
  "model_id": "deepseek-coder-33b",
  "reasoning": "Bon équilibre pour le développement logiciel.",
  "estimated_vram_required_gb": 24,
  "recommended_gpu_tier": "RTX_A6000"
}
Résilience : Si l'API OpenAI échoue, un fallback par mots-clés sélectionne un modèle approprié. La plateforme reste fonctionnelle sans clé OpenAI.

Calcul des prix

app/Services/CostCalculator.php

Formule de calcul du prix mensuel :

Prix final = (Coût de base × (1 + Marge)) + Frais fixes

Où :

  • Coût de base = (prix GPU/h × 730 h) + (stockage Go × coût/Go/mois)
  • Marge = 35 % par défaut (configurable)
  • Frais fixes = 9,99 $ par défaut (configurable)

Exemple : RTX 4090

Coût de base  = (0,79 × 730) + (50 × 0,10) = 581,70 $
Marge (35 %)  = 581,70 × 0,35 = 203,60 $
Frais fixes   = 9,99 $
Prix final    = 581,70 + 203,60 + 9,99 = 795,29 $/mois

Paiement PayPal

Deux modes de paiement sont supportés :

Abonnement mensuel

  • Création d'un produit PayPal (mis en cache)
  • Création d'un plan de facturation récurrente
  • L'utilisateur est redirigé vers PayPal pour approuver
  • Le webhook BILLING.SUBSCRIPTION.ACTIVATED active le tenant

Heures de test (pay-as-you-go)

PackHeuresPrix
1 heure13,99 $
10 heures1019,99 $
50 heures5079,99 $
100 heures100129,99 $

Les heures sont créditées via le webhook PAYMENT.CAPTURE.COMPLETED. Le custom_id de la commande PayPal contient le nombre d'heures (test_hours:{tenantId}:{hours}).

Sécurité des webhooks

PayPal : La signature est vérifiée via l'API /v1/notifications/verify-webhook-signature avant tout traitement.
RunPod : Le webhook est authentifié via un HMAC SHA-256 (X-RunPod-Signature) configurable via RUNPOD_WEBHOOK_SECRET.
Idempotence : Chaque événement PayPal est dédupliqué via son event_id (cache Redis/file, TTL 24h).

Provisionnement RunPod

Le job ProvisionRunPodPod crée un pod GPU sur RunPod avec :

  • Le GPU sélectionné (RTX 4090, A100, H100, etc.)
  • L'image ghcr.io/open-webui/open-webui:ollama
  • Le modèle LLM pré-configuré (Ollama)
  • Des identifiants admin générés aléatoirement
  • Un volume persistant pour les modèles (50 Go par défaut)
  • Un port HTTP (8080) exposé

Identifiants

Les identifiants admin sont chiffrés en AES-256-CBC avant d'être stockés en base de données. Le modèle Pod expose des accesseurs : 

$pod->decryptedUsername();  // retourne le username déchiffré
$pod->decryptedPassword();  // retourne le password déchiffré

Journal des événements

Lorsque le pod passe à l'état RUNNING, l'événement PodProvisioned est dispatché et l'email WelcomeWithCredentials est envoyé (via la queue).

Monitoring des pods

app/Jobs/MonitorPodStatus.php

Après la création du pod, un job de monitoring est dispatché avec un délai de 15 secondes. Il interroge l'API RunPod et met à jour le statut local :

Statut RunPodAction
CREATING / INITIALIZINGRe-dispatch après 15s (jusqu'à 60 tentatives)
RUNNINGMarque comme provisionné, envoie l'email
TERMINATED / FAILEDArrête le monitoring
Timeout (60 tentatives)Statut ← FAILED
Backoff : Le job utilise un backoff [15, 30, 60] secondes entre les tentatives. En cas d'erreur API passagère, il se re-dispense automatiquement.

Panel d'administration Filament

Accessible via /admin, le panel Filament permet de gérer :

Clients (ClientResource)

  • Liste des tenants avec statut d'abonnement, GPU, prix
  • Filtres par statut et tier GPU
  • Actions : voir les pods, éditer, supprimer
  • Colonnes : ID, société, propriétaire, GPU, statut, prix, profit

Pods (PodResource)

  • Liste des pods avec statut, GPU, modèle, coût
  • Actions : refresh statut, restart, pause, terminate
  • Copie du RunPod ID
  • Statuts : CREATING, INITIALIZING, RUNNING, STOPPED, TERMINATED, FAILED

Plans (PlanResource)

  • CRUD des plans GPU
  • Action "Recalculate Price" (synchronise avec la config)
  • Override de marge et frais fixes par plan

Mode test

Activable via APP_TESTING_MODE=true dans le .env. Ce mode :

  • Bypasse les paiements PayPal réels
  • Utilise SimulatePodProvisioning au lieu de ProvisionRunPodPod
  • Les achats d'heures de test sont crédités instantanément sans PayPal
  • Un pod simulé est créé avec des données fictives
Attention : Les emails sont toujours envoyés en mode test. Utiliser MAIL_MAILER=log pour le développement.

Mise en production

Prérequis serveur

  • PHP 8.2+ avec extensions : BCMath, Ctype, Fileinfo, JSON, Mbstring, OpenSSL, PDO, Tokenizer, XML, cURL
  • Composer
  • MySQL 8.0+ ou MariaDB 10.6+
  • Redis (pour queue, cache, sessions)
  • Node.js & npm (pour le build frontend)
  • Supervisor (pour le worker queue)

Installation

git clone <repo> /var/www/infrasouveraine
cd /var/www/infrasouveraine

composer install --no-dev --optimize-autoloader
npm install && npm run build

cp .env.example .env
# Éditer .env avec vos credentials
php artisan key:generate
php artisan migrate --force

# Optimisations Laravel
php artisan config:cache

process_name=%(program_name)s_%(process_num)02d

Nginx

server {
    listen 443 ssl http2;
    server_name infrasouveraine.io;

    root /var/www/infrasouveraine/public;
    index index.php;

    ssl_certificate /etc/letsencrypt/live/infrasouveraine.io/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/infrasouveraine.io/privkey.pem;

    location / {
        try_files $uri $uri/ /index.php?$query_string;
    }

    location ~ \.php$ {
        fastcgi_pass unix:/var/run/php/php8.2-fpm.sock;
        fastcgi_param SCRIPT_FILENAME $realpath_root$fastcgi_script_name;
        include fastcgi_params;
    }

    location ~ /\.(?!well-known).* {
        deny all;
    }
}

Bonnes pratiques

  • Ne jamais committer le fichier .env (dans .gitignore)
  • Utiliser un secret différent pour chaque environnement
  • Activer APP_DEBUG=false en production
  • Configurer LOG_LEVEL=warning en production
  • Utiliser HTTPS partout
  • Surveiller les failed_jobs et les logs d'erreur
  • Sauvegarder la base de données régulièrement
